# ADR-0017: SSH Transport and Git LFS Support

## Context
ADR-0014 defined HTTP transport and socket-based hook authorization for the OBS Flow native git forge, anticipating SSH support and noting the requirement that authorization logic must not be implemented twice. Additionally, distribution package maintenance frequently involves handling large upstream binary source archives (`.tar.gz`, `.tar.xz`, `.orig.tar.gz`) that must not bloat standard git commit history.

## Decision

1. **SSH Transport:**
   - **Authentication:** Public SSH keys are associated with user accounts (`SSHKey` model) and identified by their SHA256 fingerprints. OpenSSH integration is handled via standard `AuthorizedKeysCommand` or `authorized_keys` file generated by `manage.py authorized_keys`.
   - **Execution Wrapper:** A restricted shell command (`manage.py git_shell <username>`) executes incoming SSH commands. It restricts command invocation exclusively to `git-upload-pack` and `git-receive-pack`.
   - **Unified Authorization & Hooks:** The SSH wrapper reuses the exact same repository resolution (`_resolve_repo`), environment context injection (`OBS_FLOW_USER`, `OBS_FLOW_PROJECT`, `OBS_FLOW_PACKAGE`), and Unix socket hook server configuration (`OBS_FLOW_HOOKS_SOCKET` with `core.hooksPath`) established for HTTP transport in ADR-0014.

2. **Git LFS (Large File Storage):**
   - **Batch API (v1):** Implemented under `<repo>/info/lfs/objects/batch` supporting both `upload` and `download` operations with JSON payloads.
   - **Storage Scheme:** LFS blobs are stored in a content-addressable filesystem layout rooted at `GIT_LFS_ROOT`: `<GIT_LFS_ROOT>/<oid[0:2]>/<oid[2:4]>/<oid>`.
   - **Integrity Verification:** Uploads are streamed and verified on the fly via SHA-256 hash calculation against the client-provided `oid` before persisting to storage.
   - **Access Control:** LFS downloads allow read access matching repository visibility, while LFS uploads require authentication matching git push permissions.

## Consequences

**Positive:**
- Seamless command-line git workflows: developers and maintainers can use standard `git clone git@...` and `git push` over SSH using their registered SSH public keys.
- Efficient binary source archive management via standard `git-lfs` tooling without bloating bare git repositories.
- Zero duplication of push policies or hook rules: HTTP and SSH execute through the identical Unix socket hook validation service.

**Negative:**
- Requires hosting or integrating an OpenSSH daemon configured to point to `manage.py git_shell` on the server host.
- Local disk capacity planning is required for large LFS object storage (`GIT_LFS_ROOT`).
